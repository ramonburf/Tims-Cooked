# Tims Cooked

Tims Cooked is an exploratory iOS security-research harness and analysis repository for iOS 27.0 and 27.0.1 on arm64e. The research goal is a semi-untethered jailbreak; this repository does **not** contain one.

## Current status

No kernel read/write primitive, kernel code execution, PAC/SPTM bypass, or working jailbreak has been demonstrated. The repository tracks candidate socket, VM, IOSurface, and other kernel paths. Treat each result according to its evidence: a reachable interface or race observation is not, by itself, a memory-corruption primitive or exploit. A 2026-11-20 source review reclassified the earlier socket peer-delivery events as inconclusive because the trigger does not exclude ordinary file-descriptor reuse; no socket UAF is established. See the [socket fd-reuse correction](research-updates/2026-11-20-socket-fd-reuse-erratum.md).

Start with the relevant notes under [`analysis/`](analysis/) and distinguish confirmed observations from hypotheses before running a probe.

## Latest research update — 2026-11-20

Static work on iOS 27.0.1 (build 24A446) has completed an enumeration of kernel writers of the virtual-memory object “pager ready” flag bit. Two candidate producers are identified and characterised: the pager-association routine behind the freezer/pageout chain, which sets the bit only when the object’s internal flag is set, and a memory-object attribute handler reached from the system pager initialisers. Four previously unclassified candidate stores were shown to belong to VFS, network-interface, packet-buffer and Skywalk networking state rather than virtual-memory objects, so they do not affect the guarded fault predicate. Earlier the same day, static analysis connected a Mach-VM-read-like request path to a VM copy/fault candidate. Neither result is a confirmed vulnerability, controlled corruption, kernel read/write primitive, or jailbreak. No new CoW device trigger was run, and device work remains blocked because no authorised Mac currently enumerates a device.

See the [dated research note](research-updates/2026-11-20.md), the [socket fd-reuse correction](research-updates/2026-11-20-socket-fd-reuse-erratum.md), and the [GitHub checkpoint release](https://github.com/ramonburf/Tims-Cooked/releases/tag/research-2026-11-20-d). That release includes the unchanged, sanitized v0.6 IPA (SHA-256 `dd7a4680155fd738d5b279bf0da3e8debf385a0cf44d8636a0c35a3e1039ce50`); no new app build is claimed.

A later static pass re-verified, with an independently written strict address-reference scanner, which kernel functions read the interned DriverKit entitlement keys, and named the single kernel reader of the generic `IOUserClientEntitlements` key (an indirectly entered routine whose enforcement role and owning subsystem are not established). This closes the earlier open question about those readers with exact addresses instead of an inference; it does not reopen any candidate path and no device work was possible.

A later static pass revisited an AppleJPEGDriver request-processing routine that an earlier checkpoint had recorded as unreferenced and possibly dead code. That was a tooling false negative: the address-reference scanner had been handed a truncated address and returned no hits while the rest of the run looked normal. With the full address, six genuine references exist — the decoder/encoder entry bodies hand the routine's signed address to the driver's command gate as a deferred work action, so the shared request-validation checks do execute, asynchronously after the external-method call returns. This corrects the record rather than opening a path: the earlier bounded-negative conclusion stands, now resting on validators that are actually dispatched. A new open question, untested, is whether the request object can be released before the deferred work runs.

A later static pass closed the patch-diff axis of that new question. iOS 27.0.1 (build 24A446) and iOS 27.2 (build 24B119) contain the same number of functions in the AppleJPEGDriver kernel extension, and an index-paired comparison of every function's instruction stream finds no differing functions; an alignment pass that flagged 167 "changed" blocks was re-checked per function and all 167 turned out to be address/data-segment drift. The queued-I/O worker, the completion and client-teardown routines, the six decoder/encoder entry bodies and the validation chain are therefore instruction-shape unchanged upstream, so there is no patch evidence for the deferred-lifetime lead. The four imported-helper targets were disassembled (allocator-shaped, free/delete-shaped, and two object-lifetime-shaped helpers); those identities remain inference, not symbol proof. Whether anything keeps the request alive between enqueue and gate execution is still unresolved, and no use-after-free or kernel primitive is claimed.

A later source-and-log review corrected the historical socket results. The earlier precision and cross-protocol probes counted peer bytes and UDP datagrams as “stale writes”, but their sender counter advances immediately before `sendmsg` and the target descriptor is closed before reclaimer sockets are allocated, so ordinary file-descriptor reuse can produce the same output. Those events are therefore observations, not confirmed use-after-free or object-reclaim hits, and the proposed CVE-2026-112514 mapping remains unverified for this target. The detailed correction and the fd-pinned control needed before any rerun are in the [socket fd-reuse correction](research-updates/2026-11-20-socket-fd-reuse-erratum.md).

A later static pass resolved an open provenance question about the AppleJPEGDriver kernel extension. Three constants in its read-only data segment are passed as the first argument to the extension's imported allocate/free helpers, read as zero in the file, and are written by no instruction in the extension; an earlier checkpoint could not tell whether they were boot-time-constructed objects or pointer slots on a page the chained-fixup decoder misses. They are neither: each is the head of a prelinked per-class type-descriptor record (`site.<ClassName>` name reference, signature string, flags word, element size), and all three are `site.JpegRequest` records (element size `0x558`). The kernel-side helper consumes exactly that layout and treats a zero head as "use the global default typed-allocation view", so the records need no runtime construction and JpegRequest objects are type-isolated allocations. The same pass recorded a tooling caveat: the chained-fixup walk stops early in this segment and omits provably live relocated slots, so absence from the walk is not evidence that a quadword is not a pointer slot — the byte-level arguments are what settle it. No vulnerability, kernel read/write primitive, or jailbreak is established; see the [dated research note](research-updates/2026-11-20-applejpeg-descriptor-provenance.md).

A later static pass examined the lifetime of that request object and recorded a candidate hazard, still unconfirmed. All six reachable decoder/encoder entry bodies allocate one request, hand it to the driver's command gate as deferred work, and then release it unless two conditions hold together: the caller's input source field is non-NULL and the enqueue returned success. When that input field is NULL — which an app controls, and which lies inside the declared input size — the release runs even on success, after the object has been passed to the deferred worker, whose first act is to read that same field and which writes further fields later. The imported release helper was disassembled and is a real typed free (zone derived from the object address, stored-size check, kernel free tail-call), and the extension's own completion path releases finished requests with the same helper, so the asynchronous pipeline does take ownership elsewhere. What decides whether this is a defect is unresolved: if the command gate executes these actions inline the release is correct, and if the deferred worker always rejects a NULL source field the release is ordinary error cleanup. No device was available, nothing was executed, and no use-after-free or kernel primitive is claimed; see the [candidate note](research-updates/2026-11-20-applejpeg-request-lifetime.md).

A later static pass closed that candidate as a bounded negative. IOKit's command gate does not defer its action: `runAction` takes the workloop gate and invokes the supplied routine inline on the calling thread, returning only after it returns, so there is no window in which the caller releases an object still pending in the gate. In the target extension, when the request's source field is NULL the queued-I/O worker takes an explicitly synchronous branch — it sleeps on the command gate until the completion path sets a flag in the request, then returns the stored status — and the completion routine wakes the waiter in that case but skips its own free, freeing only when the source field is non-NULL (the asynchronous case where the caller has retained ownership). A whole-extension scan confirms the shared bookkeeping helper never calls the typed-free stub. The earlier hazard reading rested on assuming deferred dispatch; that assumption was wrong. This retires the request-lifetime lead and its planned device oracle; no kernel read/write primitive, kernel code execution, or jailbreak is demonstrated, and no device probe was run. See the [resolution note](research-updates/2026-11-20-applejpeg-request-lifetime-resolution.md).

A later static pass re-opened and then re-closed the Neural Engine direct-access question by reading the kernel's own published classes instead of inferring them from names. The earlier checkpoint had measured one openable Neural Engine service and dismissed it as a power/load-management helper on the strength of its class name; because substring reasoning about kernel classes has misled this project before, the extension's `IOKitPersonalities` were read directly from the kernelcache's prelinked information. They show that the personality keyed `ANEDriver` instantiates the load-balancer class, matched through the resource plane, while the engine class is published separately through the RTBuddy and ARM I/O planes. The service the device sweep opened is therefore the load balancer, exactly as the earlier note assumed, and the engine class exposes no external-method table entry that the measured opens could have reached. The direct route stays closed; a CoreML-driven route remains possible in principle but is a large unstarted sub-project. A census joining every cross-build-changed extension to its published service classes is included as reconnaissance only. No vulnerability, kernel read/write primitive, or jailbreak is established, and no device probe was run; see the [personality-map note](research-updates/2026-11-20-ane-personality-map.md).

A later static pass settled two open questions about the kernel's generic user-client entitlement gate. An earlier checkpoint had located the routine that reads the property but could not tell whether it enforced anything or merely queried it, nor whether it sat on the user-client open path. Enforcement is now established from string ownership rather than from the call graph: all six user-client refusal messages in the kernel image (missing property, value not boolean-false-or-string, missing entitlement in process, failed MACF, failed sandbox, and the default-locking requirement) are referenced from that one routine, and it stores a refusal code through a caller-supplied output slot while returning success itself. Its only direct caller is a message-dispatched request/reply handler that validates a fixed-size request record, invokes the gate, and writes the verdict into a reply record, so the check runs on an indirectly entered server path rather than as dead code. Three independent scans over the whole kernel image found no ingress to that handler or its siblings, each validated with a positive control; the registering routine table was not located. This closes the earlier question with exact evidence but does not reopen any candidate path, and no vulnerability, kernel read/write primitive, or jailbreak is claimed; see the [enforcement note](research-updates/2026-11-20-iouc-entitlement-enforcement.md).

A later static pass closed the open item from that checkpoint by identifying the dispatcher instead of hunting for its registration table. The routine is the kernel's generic user-client external-method dispatcher: it validates an extension's declared scalar and structure counts against the argument record a sandboxed app supplied, then calls one of several marshalling shims by method flavour, and the shim-name consumer sits directly beneath it. A whole-image pointer-slot search finds no stored reference to it in any data segment, including boot data, while a positive control reproduces a known slot — so the reference is a fixup entry the decoder misses or a runtime-built table, which is recorded as a tooling gap rather than as dead code. Pairing every function in that family with its iOS 27.2 counterpart shows identical instruction streams throughout, so the most app-reachable surface in the image — app method-call validation, marshalling and entitlement gating — carries no 27.0.1-to-27.2 fix and offers nothing to adopt as a candidate. No vulnerability, kernel read/write primitive, or jailbreak is established; see the [dispatch cross-build note](research-updates/2026-11-20-iouc-dispatch-crossbuild.md).

A later static pass took the open "highest-value unexamined changed extension" step from that reconnaissance and examined an extension that publishes an enumerable service plus a user client. Filtering the cross-build census to extensions whose function count is identical in both builds, then re-checking every flagged region per function, leaves exactly one contiguous region of real edits: nineteen functions forming that user client's external-method dispatcher and handler bodies, seventeen of them differing at the instruction level. In each handler the newer build inserts three instructions ahead of pre-existing checks — load a per-request word, clear bit 8 of it, store it back — and hoists the rejection-status constant into the prologue. The user client requires a private entitlement string on its open path, and no device sweep has established whether an unsigned app can satisfy it. What that request-word bit means, who sets it in the target build, and whether any reachable input can leave it set are unresolved; no out-of-bounds access, type confusion or lifetime error was observed, and no vulnerability, kernel read/write primitive, or jailbreak is claimed. See the [user-client handler note](research-updates/2026-11-20-applecentauri-userclient.md).

A later static pass identified that changed family. It is the driver class's slot-12 virtual override, which this project had already characterised in a closed investigation as the DriverKit-style `Dispatch(const IORPC rpc)` entry — not the external-method table. The override routes on the kernel-supplied RPC content's message identifier to its own method bodies. In the newer build the two size constants are minimum thresholds on the RPC's declared send and reply sizes, so neither is an unbounded caller-controlled length; and the inserted three-instruction sequence clears reserved message-flag bit 8 ahead of the pre-existing gates, the same mask, position and idiom as the two other slot-12 `Dispatch` overrides in the closed cluster. The kernel dispatcher code confirms the external-method row stride and field roles quoted earlier rather than leaving them inferred. App reachability is not established: slot-12 `Dispatch` sits behind DriverKit RPC machinery that an earlier bounded-negative pass found reachable only through a DriverKit-administrator-gated creation path, and the driver's user client requires a private entitlement to open. No vulnerability, memory-safety effect, kernel read/write primitive or jailbreak is claimed, and no device probe was run; see the [dispatch-owner follow-up](research-updates/2026-11-20-applecentauri-dispatch-owner.md).
A later static pass completed a whole-member census of the kernel core between the target and newer builds, then stripped recompilation noise with two independent clusterings. After removing register-allocation and stack-slot artefacts, the only systemic change left is the already-characterised reserved message-flag bit-8 clear in kernel `Dispatch` overrides; a numeric multiply-by-constant change in a per-CPU statistics gatherer is a structure-size change, not validation logic. The census also surfaced one new fix-shaped candidate, unconfirmed: in a small function family that walks a linked list of fixed-size entries from an authenticated descriptor, the newer build inserts a per-entry bound assertion (`count * 0x18 + 0x18` against a descriptor-derived limit) before dereferencing, while the target build walks without it. The owning subsystem, attacker control of the count and limit, and any sandboxed-app ingress are all unresolved, so no out-of-bounds access, kernel read/write primitive or jailbreak is claimed and no probe was run; see the [kernel-core census note](research-updates/2026-11-20-kernelcore-delta-census.md).

A later static pass identified that fix-shaped family by structure rather than by strings or symbols, and closed it as a bounded negative. It is the Mach IPC port-name table accessor set (the routines that look up, reserve, claim, allocate and resize entries in a task's IPC space): the code authenticates a self-describing table pointer, each entry is `0x18` bytes with its free-list link at `+0xc`, one member derives a table index from a port name and checks the stored generation and capability-type fields, and another applies a load-factor threshold and walks the free list, returning `KERN_NO_SPACE`. The newer build adds per-access index bounds assertions before dereferencing index-derived entries, plus a null check and a reordered type/generation comparison in the lookup. This is defence-in-depth rather than an app-triggerable defect: the user-influenced lookup index is already bounds-checked in both builds, the reservation and claim paths walk kernel-owned free-list state, and no attacker-chosen value reaches an unvalidated dereference. No device was enumerated and nothing was executed; no vulnerability, kernel read/write primitive, or jailbreak is claimed. See the [port-name table hardening note](research-updates/2026-11-20-ipc-entry-table-hardening.md).

A later static pass audited the largest unexamined changed kernel extension and closed it as a bounded negative. The SCSI architecture-model extension carried the highest nominal index-paired change count in the cross-build census (248 functions), but both builds contain the same number of functions, and a per-function shape re-check reduced 56 flagged regions to 54 cases of address/data-segment drift and only 2 real edits. Both real edits are internal lifecycle refactors on an unpublished SCSI task object: a teardown routine gains an unconditional field clear plus a state-gated notification through an imported kernel stub, and a small helper that stored back-pointer/state fields was inlined into its constructor with the same notification added first. The extension publishes no user-client class, and the changed teardown routine has no direct caller in either build. No out-of-bounds access, lifetime error, kernel read/write primitive or jailbreak is established, and no device probe was run; see the [SCSI member audit note](research-updates/2026-11-20-scsi-member-audit.md).

## Safety

- Test only on devices you own or are authorized to assess.
- The research workflow is intended to preserve device data. Do not restore, update, downgrade, or write firmware as part of these probes.
- A kernel or system-service probe can still crash or reboot a device. Stop after a crash, respring, or unexpected reboot, then preserve the logs before continuing.
- Review a probe and its resource limits before running it. Do not treat a successful launch or a userland crash as proof of kernel impact.
- Keep signing credentials, device identifiers, host details, and private operational notes out of commits.

## Release 0.6

The `v0.6` release asset is `TimsCooked-v0.6.ipa` (build 6, bundle identifier `com.example.timscooked`). It is an ad-hoc-signed research build with no embedded provisioning profile. Re-sign and provision it with your own development identity before installation. It is a harness for research, not a jailbreak or a general-purpose security tool.

## Build and run

Building requires macOS and Xcode. Installing on a device also requires a locally configured signing identity and a device enabled for development.

From the `carrier/` directory, build for a connected device:

```sh
cd carrier
DEV=<device-identifier> ./build_race.sh
```

The script writes the app to `.build13/Build/Products/Debug-iphoneos/AGXProbe.app`. Install and launch it with the bundle identifier configured in your local Xcode signing settings:

```sh
xcrun devicectl device install app --device "$DEV" \
  .build13/Build/Products/Debug-iphoneos/AGXProbe.app
xcrun devicectl device process launch --device "$DEV" --console \
  --terminate-existing <your-bundle-identifier> --sockprec
```

The build helper accepts `KEYCHAIN_PW` from the environment when Xcode needs the login keychain unlocked. Do not put the password in the script or in shell history. Signing settings belong in your local Xcode configuration, not in this repository.

### Harness modes

| Argument | Purpose |
|---|---|
| `--sockuaf` | Run the socket-lifetime race variants |
| `--sockprec` | Run the gated socket probe with its peer-delivery oracle |
| `--sockool`, `--sockxz`, `--sockgc` | Run experimental reclaim and spray variants |
| `--web`, `--webscan` | Run WebKit probes |
| `--probe` | Run the IOSurface probe sweep |

These modes are experimental and may crash the app or device. Their names describe what a probe attempts, not a confirmed vulnerability or exploit.

## Tests

The standalone Swift regression checks do not require a device or signing. Run them on macOS:

```sh
cd carrier/tests
swiftc -O fixcheck.swift -o "$TMPDIR/fixcheck" && "$TMPDIR/fixcheck"
swiftc -O logcheck.swift -o "$TMPDIR/logcheck" && "$TMPDIR/logcheck"
```

See [`carrier/tests/README.md`](carrier/tests/README.md) for test coverage and limits.
